# Display service parity inventory

The historical inventory below describes source behavior at Amaterasu `6d490593192e944fd6f865a89c1ce0ed5d89bf4f` and the pinned Vibeshine reference `3ed14cda3c5a6f622173200287faabe811cfedb1` (see [configuration execution plan](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/docs/configuration-execution-plan.md)). It is not a claim of end-to-end parity or hardware qualification. Native modules are trusted code; service grants are not a native-code sandbox. The service contracts are Amaterasu APIs, not Vibeshine APIs.

## Current extension behavior and evidence

The independently built extension owns display policy and delegates native operations through the public Amaterasu services. For the supported cooperative Linux Wayland virtual-display path, it plans a session-owned display before application launch, binds each stream to an independently validated native borrow, retains the session reference across pause, and releases it at session end. Same-mode and changed-mode resume use coordinator-admitted operations; changed-mode resume records a durable intent and checks the native result before publishing the new binding. The registered `remove-owned` action is available through the generic action service. Other display actions are not advertised.

An actual plugin, broker, and lifecycle coordinator have been exercised together with simulated native display and state services, including session and stream preparation, pause, same-mode resume, changed-mode resume, and cleanup. This is integration evidence for those simulated peers, not a live device or hardware qualification. The native reconfigure recovery path only queries the original recorded operation; unknown outcomes remain fenced. If resizing succeeds but stream preparation is interrupted before a candidate is published, the checkpoint can be reconciled but the partial preparation remains `recovery_required` pending a typed cleanup transition.

Paused session ownership is supported for the default `until_session_ends` policy. The separate keepalive, enforcement, and timed-retention settings are currently rejected during planning. Linux physical mutation remains gated, and physical observation refresh is unavailable. Windows, HDR, scaling, compositor interoperability, and native restoration still require the platform-specific work and hardware checks listed below. The cooperative lease and topology checks fence known Amaterasu consumers; unrelated desktop processes and operating-system changes can alter native state outside that authority.

Physical apply captures a baseline and durably journals it through `amaterasu.state/1` before effects. Revision checks detect changed topology; exact operation-ID retries do not repeat effects. Restoration is verified before clearing the journal, and an uncertain or failed restoration retains recovery state. A module restart requires explicit recovery. The state call grant is needed by both provider and originating caller. See [pipeline](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/display/src/pipeline.rs) and [README](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/display/README.md).

On Windows, physical enumeration, CCD application, HDR readback and restoration have native source implementations. Snapshots preserve paths, modes, topology and available HDR state; unsupported or ambiguous recovery fails closed. Active-monitor mode enumeration is available, but inactive-target mode enumeration is not. On Linux/KDE, enumeration and snapshots query the user session's KScreen state. A bounded KScreen mutation and recovery implementation exists, but `supported()` remains false, so physical mutation is gated. Other platforms are unsupported. See [Windows provider](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/display/src/platform/windows/mod.rs), [Windows query](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/display/src/platform/windows/query.rs), [Linux provider](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/display/src/platform/linux.rs) and [provider selection](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/display/src/platform/mod.rs).

Windows virtual display uses a private durable journal, random capability and exact driver lease. Restart reclaims matching ownership with fencing; uncertain creation or removal is reconciled instead of replaying an ambiguous create. The driver lease is periodically fed, and cleanup retains records until departure is confirmed. A recovered monitor without its original CCD binding is not advertised capture-ready. Creating a virtual monitor does not itself activate Windows topology. See [manager](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/virtual-display/src/manager.rs), [journal](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/virtual-display/src/journal.rs), [driver backend](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/virtual-display/src/backend/windows.rs) and [protocol](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/virtual-display/src/protocol.rs).

The optional Linux libvirtualdisplay backend uses the existing UID-enforcing broker and an exclusive per-user journal. It selects an unoccupied connector, journals before connecting, configures KScreen, and verifies output state. Extended placement preserves the current desktop; exclusive placement saves the baseline, disables non-owned outputs, and retains other journaled streams. Removal and interrupted startup reconciliation retain recovery intent on failure. The current code forwards HDR and supports retained, automatic and fixed scale requests in its KScreen target; actual compositor and hardware support is a separate qualification gate. The [virtual-display README](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/virtual-display/README.md) contains older descriptions of Linux layout, HDR and scaling; prefer [Linux worker](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/virtual-display/src/linux_manager/worker.rs), [compositor](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/virtual-display/src/linux_manager/compositor.rs), and [scale model](https://github.com/Nonary/amaterasu/blob/6d490593192e944fd6f865a89c1ce0ed5d89bf4f/modules/virtual-display/src/scale.rs) for these behaviors.

## Historical reference comparison and remaining work

| Area | Pinned reference and current gap |
| --- | --- |
| Configuration and policy | Vibeshine parses display configuration, resolution, refresh, HDR, virtual mode and layout settings in `src/config.cpp` at the pinned revision. Amaterasu's typed policies and service requests do not by themselves establish complete persisted global/application/client projection, precedence, UI readback, or the Moonlight optimize-settings gate.
